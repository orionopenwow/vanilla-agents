## Implementation notes (Stage 1)
- I-001 Controller lock uses `msvcrt.locking` (Windows) / `flock` elsewhere on byte 0 of `controller.lock`. The owner record sits after byte 16 and is informational. A clean shutdown clears it; a record left behind means a crash and produces a `controller_takeover` event at the next start.
- I-002 Checkpoint classification: `not_due`, `consistent`, `missing`, `stale`, `ahead`, `inconsistent`. A checkpoint older than the database is legitimate; `ahead` means the database lost events (restore or truncation).
- I-003 Evidence publication uses rename (never replace). An existing artifact is re-hashed and refused if it does not match its name. Interrupted publications leave either a temp file (removable) or a published orphan (reported, never auto-deleted in Stage 1).
- I-004 A new claim for the same (task, criterion, check) automatically supersedes the previous current claim.
- I-005 Stage 1 has no real verifier: every claim and qualification in the tests comes from a labelled fixture verifier and says nothing about any real project.
- I-006 Fencing: `require_fence` rejects any token older than the newest for that resource, or not carried by a held lease.

## Stage 2: trusted verification runner
| ID | Decision |
|---|---|
| D-033 | The verifier is a separate subprocess that never touches the database. The controller (single writer) validates its result bundle and stores evidence, run record, claims and the state change in ONE transaction. A refused, crashed, truncated or mismatched run writes nothing. |
| D-034 | Protected files (tests, scripts, configs per the trusted list) are restored from the base commit before checks run, so a worker cannot make its own work pass by editing the checks. ## Stage 3: durable execution
| ID | Decision |
|---|---|
| D-048 | Fencing is enforced inside the storage transaction: transition_execution, block_task, create_attempt and transition_attempt take an optional fence=(resource_type, resource_key, token); a token that is stale, not on a held lease, expired, or held by another task is rejected (StaleFence, audited) and nothing changes. fence=None stays unfenced for callers that hold no lease. require_fence shares the same check. External processes still cannot be fenced (D-022). |
| D-049 | Scheduler: next task = QUEUED and not cancelling, ordered by (created_at, task_id), read from stored state only. claim_next leases one resource then moves the task to LEASING; start_run creates the attempt and moves to RUNNING, every step fenced. A busy resource waits (no skipping later tasks). |
| D-050 | Watchdog with an injectable clock (never sleeps): an expired held lease, a RUNNING task whose worker has not heartbeat for stuck_after, or a task stuck in LEASING is orphaned: attempts become LOST, workers termination_requested, leases release_pending, task BLOCKED(worker_unreachable). Cancelling tasks are left to the cancellation lifecycle. |
| D-051 | Restart recovery orphans every task with anything in flight (a new controller owns none of the old workers), in (created_at, task_id) order, then settles. The controller cannot prove a process is dead, so the caller supplies is_terminated(worker_id) (default: never): only then are workers confirmed terminated, leases released and the task requeued to QUEUED. Every step checks current state first, so a repeat run changes nothing and writes no events. |
| D-052 | Disk preflight: check_disk(path, min_free_bytes) raises DiskSpaceLow (disk_space_low) when free space on the path drive (nearest existing parent for a missing path) is below the threshold; the threshold is always a parameter, never a constant. |

## D-120 (2026-10-17, the owner's budget constraint) No automated headless workers; vanilla-agents is verifier + scheduler only
the owner has no money for extra usage. Decision: real launching (RealLauncher, enable_real) stays OFF. Work is done by interactive Claude Code sessions/subagents inside the owner's normal plan; vanilla-agents verifies their output (Stages 1-4). Headless `claude -p` is not used unless the owner later confirms in writing that it bills against the plan, not API credits. Reviews use fresh-context Claude agents (Codex unavailable). Prefer smaller models (Sonnet/Haiku) for routine helpers; reserve strong models for security/architecture review.

## D-121 (2026-10-17) Real trusted folder ~\.vanilla-agents\trusted built by scripts/make_trusted.py

## D-130 (2026-10-17) Event feed: JSONL file, one schema, cursor reads (build step 3)
Package vanilla_agents/events/. One versioned schema (v1, 14 event types, flat string data, used_pct numeric). Feed is an append-only JSONL file; ids rise by 1 across processes under an OS byte-range lock; one os.write per line; read_since(cursor) takes a caller-held cursor, no polling inside. Size cap 1 MB, 3 rotated files kept. Every string is redacted (vanilla_agents.verify.redact) and capped at 2000 chars BEFORE write. UI reads events only, never the DB (DESIGN 7.5).

## D-131 (2026-10-17) Derived events use audit seq ids, not feed ids
derive.py maps the audit log read-only (connect_ro) to the same schema for startup reconstruction; ids are audit seq. The UI loads derive + current_state once, then follows Feed from last_id(). The two numberings are never mixed.

scripts/claude_hook.py swallows every exception (BaseException), prints nothing, exits 0, and a 3 s watchdog thread calls os._exit(0) if the feed lock is held. Settings.json is documented in docs/HOOKS_SETUP.md, never edited by us.
